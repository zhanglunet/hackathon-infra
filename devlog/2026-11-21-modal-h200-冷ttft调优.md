# 2026-11-21 Modal H200 冷 TTFT 调优：272K 首请求 51 秒 → 目标 15 秒

> 日期：2026-11-21（JST 23:17–23:45，UTC 14:17–14:45）
> 模型：Qwen3.8-27B-FP8（`Qwen/Qwen3.8-27B-FP8`，served 名 `qwen3.8-27b`），vLLM 0.34.0，Modal H200
> 探测输入：同一份《白鲸》正文，tokenizer 数准 271,500 token（模板化后）+ 64 输出 token；冷请求开头改一个字强制不命中缓存（与上轮第二次做法一致）
> 部署地址：`https://zhanglunet--qwen27b-vllm-serve.us-east.modal.run`（每轮测完即停）

## 目标修正（本轮开始前确认）

SLO 三档按**测试场景**分（P90 底线，组织方测试标准文档原文）：

| 场景 | 长度 | 缓存命中 | TTFT 上限 |
| --- | --- | --- | --- |
| 智能体 | 混合，最长 256K，平均 50K/1K | 0.70 | **15 秒** |
| 编程 | 混合，最长 256K，平均 100K/2K | 0.9 | **15 秒** |
| 长文本生成（SPEED-Bench） | 1K/8K | 0 | 10 秒 |
| 高压稳定验证 | 定长合成集 32K/1K | 0 | 20 秒 |

272K 是「所有模型服务端必须统一支持 272K 上下文、严禁私自截断」的硬性要求，不是单独一个测试场景。**272K 单请求的适用档是 15 秒**（20 秒只适用于 32K 高压测试，不能当目标）。另：智能体场景缓存命中 0.70 时 P90 落在未命中那 30% 里，冷 TTFT 必须真打下来，光靠热缓存不够。

**目标：冷 TTFT ≤ 15 秒，即从 51.72 秒提速 3.4 倍以上。**

## 基线（上轮已测，不重测）

| 指标 | 数值 |
| --- | --- |
| 冷 TTFT | **51.72 秒 / 53.39 秒**（两次） |
| 热 TTFT（前缀缓存命中） | 2.36 秒 |
| TPOT | 14.7–14.8 毫秒 |
| 有效 prefill 速度 | 约 5,200 token/秒 |
| KV 总容量 | 2,955,530 token（单请求占约 9.2%），可用 KV 95.41 GiB，权重 28.69 GiB |

换算：27B 稠密模型 prefill 约 2×27e9×271,500 ≈ 1.46e16 FLOPs；H200 FP8 峰值约 1,979 TFLOPS；51 秒 ≈ 290 TFLOPS 有效算力，**仅约 15% MFU**——prefill 是计算密集型，但跑得很不满。这是本轮调优要解释的核心异常。

## 第 1 轮：MAX_NUM_BATCHED_TOKENS=262144（失败）

- 配置：`--max-num-batched-tokens 262144`（271,500 token 提示只切 2 片，基本不分片），其余与基线一致。
- 结果：**引擎核心初始化连续失败 3 次以上**（EngineCore pid 32、33 失败，容器多次重启；日志最后反复出现 "Encoder cache will be initialized with a budget of 262144 tokens, and profiled with 16 image items of the maximum feature size"，随后 "Engine core initialization failed"；根本原因异常未在滚动日志窗口内看到，疑似 262K-token 规模的内存 profiling/编码器缓存预算导致初始化期内存压力）。
- 处理：约 14:26 UTC 停部署（`modal app stop qwen27b-vllm`），约 6–7 分钟 H200，约 $0.53。
- 结论：**262144 不可用。**

## 第 2 轮：MAX_NUM_BATCHED_TOKENS=65536（基本无效 + 一个测量教训）

- 配置：`--max-num-batched-tokens 65536`（271,500 token 约切 5 片，默认 8192 的 8 倍），其余与基线一致。部署 14:25:50 UTC，/health 200 于 14:29:15（try 9）。
- 结果：
  - **冷 TTFT 50.92 秒**（TPOT 14.4 毫秒）——相对基线 51.72 秒只快 1.5%，基本无效。
  - 热 TTFT **50.88 秒**（TPOT 15.1 毫秒）——初看像缓存失效，但随后诊断证明是测量假象（见下）。
  - 追加第三次相同请求：**TTFT 2.31 秒**——前缀缓存本身正常。
  - 引擎进展正常，零初始化失败；可用 KV 86.54 GiB（8192 时 95.41 GiB，单步激活多占约 9 GiB，符合预期）。
- **多容器教训（本轮最大发现）**：事后 `modal app list` 显示该部署有 **4 个 task** 在跑。Modal web 端点默认按需扩容，请求被负载均衡到不同容器：冷请求去了容器 A（全量 prefill，50.92 秒），热请求去了另一个空缓存容器（全量 prefill，50.88 秒），第三次请求又回到有缓存的容器（2.31 秒）。`/metrics` 的 `prefix_cache_queries_total` / `prefix_cache_hits_total` 读数 0.0 也是同一原因——那次读数落到了另一个容器上。
  - 同一问题还顶满了工作区 10 GPU 并发上限（serve 函数一度占到 10 张卡；部署交接时新旧容器重叠 + 端点自动扩容）。
  - **修复（已进代码）**：`serve` 函数加 `max_containers=1`，强制单容器；同时每轮测完立刻停部署、同一时间只留一个部署。
- 费用：约 7–8 分钟 H200，约 $0.55。

## 第 3 轮：65536 + VLLM_COMPILE（mode=3）（无效：编译未生效）

- 配置：`--max-num-batched-tokens 65536` + `--compilation-config '{"mode": 3}'`（VLLM_COMPILE，vLLM 定制的 Inductor 后端）。`mode` 取值已按 vLLM 官方文档 Engine Arguments `--compilation-config` 一节核实（`-cc.mode=3` 等价于 `-cc='{"mode":3}'`；0=NONE、1=STOCK_TORCH_COMPILE、2=DYNAMO_TRACE_ONCE、3=VLLM_COMPILE）。部署 14:34:38 UTC，/health 200 于 14:37:40（try 8）。
- 结果：
  - **冷 TTFT 51.76 秒**（TPOT 15.3 毫秒）——与基线 51.72 秒、第二轮 50.92 秒无差别。
  - **热 TTFT 2.45 秒**——单容器下缓存命中正常，`max_containers=1` 修复验证通过（本轮 `modal app list`：1 个 deployed，1 个 task）。
- **编译未生效（已证实）**：启动命令行确有 `--compilation-config {"mode": 3}`；APIServer 解析的配置 `mode=VLLM_COMPILE (3)`；但 EngineCore 初始化时的最终配置是 **`mode=NONE (0)`**，日志里无任何 Inductor 编译活动（无 Compiling/torch.compile 相关日志），CUDA 图（PIECEWISE，11 张）照常捕获。vLLM 在引擎初始化阶段把 mode 3 静默重置回了 0，且无 fallback/downgrade 警告。
  - 降级原因**未定位**：`vllm/config/compilation.py`（上游源码）里没有 `mode = CompilationMode.NONE` 的显式重置；疑似 `VllmConfig.post_init` 的模型级回退（混合 GDN/Mamba 层 + FP8 自定义算子可能不支持分段编译），未证实，不作断言。
- 费用：部署 14:34–14:41 UTC，约 7 分钟 H200，约 $0.53。

## 结论与下一步（按优先级）

1. **先 profiling 再猜参数。** 约 15% MFU 是核心异常：分片步长（8192→65536）几乎不改变 TTFT，说明瓶颈不在 chunked prefill 调度；Inductor 本次又没生效。下一轮先用 vLLM 自带手段定位瓶颈（`enable_mfu_metrics`、layerwise nvtx tracing、或 torch profiler 短跑），再决定动哪个变量。头号嫌疑：**GDN（线性注意力）层**——FlashInfer GDN prefill 是 JIT 编译内核，混合注意力模型里它可能拖慢整个 prefill；单变量试 `--gdn-prefill-backend triton`（日志原话提示的替代项）。
2. **试 mode=1（STOCK_TORCH_COMPILE）**，走标准 torch.compile 路径，看是否同样被降级回 eager；或直接定位 `vllm/config/__init__.py` 的 post_init 里把 mode 重置的条件。
3. **核对 P90 到底按什么提示长度算。** 若 P90 是按场景分布算（智能体平均 50K、编程平均 100K），按 5,200 tok/s 计 50K 提示约 9.6 秒（已进 15 秒）、100K 约 19 秒（还差一点）——这个口径问题决定 15 秒目标是否真需要 3.4 倍提速，需组织方文档确认，不是调参能解决的。
4. **不要做的**：更大 `max_num_batched_tokens`（262144 已证实初始化失败）；并发压测、精度测试（不在本轮范围）；升级 Modal 套餐（10 GPU 并发上限靠 `max_containers=1` + 单部署操作已可避开）。
