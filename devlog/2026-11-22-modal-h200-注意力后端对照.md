# Modal H200 冷 TTFT 调优第 5 轮：全注意力后端对照（FlashInfer / Triton vs FA3）

- 日期：2026-11-22
- 部署：Modal H200 141GB，Qwen3.8-27B-FP8，vLLM 0.34.0，MAX_MODEL_LEN=272000（YaRN 外推）
- 配置（三个后端一致）：`MAX_NUM_BATCHED_TOKENS=65536`，`VLLM_USE_BREAKABLE_CUDAGRAPH=0`，不设 COMPILATION_MODE；max_containers=1
- 全部署已停并复核：`modal app list` 0 deployed、/health 404

## 结论先行

- **FA3（对照，默认后端）：冷 52.52 / 54.94 秒、热 2.29 秒**——与第 4 轮（53.64 / 55.76 秒）同一区间，15 秒目标仍远。
- **FlashInfer：引擎起不来，0 数据。** 不是模型不兼容，是镜像里没有 nvcc：FlashInfer batch-prefill 要在引擎 warmup 时 JIT 编译 CUDA 内核，`debian_slim + pip install vllm` 的镜像里没有 CUDA toolkit，`RuntimeError: Could not find nvcc and default cuda_home='/usr/local/cuda' doesn't exist`。要测它须先给镜像加 nvcc（本轮没做，见 §6）。
- **Triton：能跑，但慢得多。冷 252.0 / 252.41 秒、热 4.25 秒**——冷 TTFT 是 FA3 的约 4.8 倍，TPOT 23 毫秒也比 FA3 的约 16 毫秒慢。Triton attention 是通用实现，长 prefill 上拼不过 FA3 的融合内核。
- **FA3 仍是最快**。本轮没有找到比 FA3 更快的全注意力后端；瓶颈仍在 FA3 prefill 本身（约 33 秒/65%），下一步须换别的方向（见 §6）。

## 事前核实（未上 GPU，读 vLLM 0.34.0 源码）

核实对象：`vllm/v1/attention/backends/registry.py`（AttentionBackendEnum）、`vllm/v1/attention/backend.py`（基类 validate_configuration）、`vllm/v1/attention/backends/flashinfer.py`、`vllm/v1/attention/backends/triton_attn.py`、`vllm/platforms/cuda.py`（get_attn_backend_cls）、`vllm/engine/arg_utils.py`（`--attention-backend`）、模型 config（`Qwen/Qwen3.8-27B-FP8` 的 text_config）。

模型事实：64 层，16 层全注意力 + 48 层 GDN 线性注意力（3 线性 + 1 全注意循环）；全注意力 head_dim 256、24 Q 头、4 KV 头；无滑动窗口；bf16 激活、fp8 KV。

- **FLASHINFER 可用（源码口径）**：`get_supported_head_sizes()` = [64, 128, 256, 512]（本模型 256 在内）；`supported_kv_cache_dtypes` 含 fp8；`supported_dtypes` 含 bf16；算力要求 SM80–SM12.1（H200 是 SM90）；非 MLA、无滑动窗口、无 sink、无稀疏，均无冲突。
- **TRITON_ATTN 可用（源码口径）**：`supports_head_size` 为 head_size ≥ 32；fp8 KV 在支持列表；算力不限；bf16 支持。
- **显式指定不会静默回退**：`cuda.py` 的 `get_attn_backend_cls` 在指定后端无效时直接报 ValueError（带原因），有效时记 `Using %s backend.` 日志——这是本轮认后端切换的证据口径。
- `--attention-backend` 只影响 16 层全注意力；GDN 线性层走自己的线性注意力后端选择（`--gdn-prefill-backend`），不受影响。
- 注意：源码核实只能证明“配置合法”，不能证明“镜像里有编译器”——FlashInfer 的失败正好卡在后者（见 §4）。

### ② FlashInfer：初始化失败，放弃

- App：`ap-gXgfKK8ybq596c0dxtc1bk`，创建 03:59 UTC，/health 28 次轮询（约 9.5 分钟）始终 000，停 04:09 UTC。
- 日志证据：APIServer 解析到的参数里 `'attention_backend': 'FLASHINFER'` 已传入；引擎在 `Warming up FlashInfer attention.` 后崩溃：
  - `vllm/model_executor/warmup/kernel_warmup.py:120 _warmup_flashinfer_attention` → `flashinfer/prefill.py:4191 plan` → `get_batch_prefill_module` → `flashinfer/jit/core.py build_and_load` → `cpp_ext.py:263 generate_ninja_build_for_op` → `get_cuda_path`
  - 根因：`RuntimeError: Could not find nvcc and default cuda_home='/usr/local/cuda' doesn't exist`（04:01:25，`EngineCore failed to start.`，随后 `RuntimeError: Engine core initialization failed.`）。
- 判定：这是镜像缺 CUDA toolkit 的环境问题，不是后端与模型不兼容。源码核实里 FlashInfer 的配置校验全部通过（§2），引擎也接受了该后端、走到了 warmup。按任务规则“初始化连续失败 2 次放弃”——第二次相同部署必定撞同一缺口，不再烧钱重跑，直接放弃并记录。修复路径见 §6。
- 费用附记：这次失败部署从创建到停约 10 分钟（含 9.5 分钟健康轮询等待），约 $0.76，是本轮最贵的一项。
