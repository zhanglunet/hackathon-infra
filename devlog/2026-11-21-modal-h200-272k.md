## 实测结果

### ① 装得下：是，没有 OOM

- 引擎启动日志：可用 KV 缓存 95.41 GiB；GPU KV 缓存总容量 2,955,530
  token，272,000 token 的请求单次并发倍数 10.87x（即一个 272K 请求
  只占 KV 约 9.2%）。权重占 28.69 GiB，峰值激活 1.73 GiB。
  引擎初始化 50.69 秒。
- 三次长请求（冷、热、无缓存冷）全部跑完，无 OOM、无报错。

### ② TTFT：冷请求爆 SLO，热请求轻松过

| 请求 | TTFT | 对 SLO（15/10/20 秒三档） |
|---|---|---|
| 冷请求（完整 prefill，271,500 token） | 51.72 秒 | 全档失败，约是最宽 20 秒档的 2.6 倍 |
| 热请求（同一提示，prefix caching 命中） | 2.36 秒 | 全档通过 |
| 冷请求 v2（改开头、强制不命中缓存，271,514 token） | 53.39 秒 | 全档失败，与第一次冷请求一致 |

- 两次冷请求互相印证（51.72 / 53.39 秒），有效 prefill 速度约
  5,200 token/秒。冷 TTFT 是本次最大短板。
- 另：`vllm:kv_cache_usage_perc` 在请求结束后读回 0.0——该指标只计
  不可驱逐的占用，已缓存的前缀块算可驱逐，不计入；热请求 TTFT
  从 53 秒掉到 2.36 秒本身证明前缀缓存是工作的。

### ③ TPOT：通过，余量约 5 倍

- 冷 14.7 毫秒、热 14.8 毫秒、冷 v2 14.7 毫秒，均远低于 75 毫秒门槛。

### 备注

- 本次只测延迟不测回答质量：模型是思考型，max_tokens=64 时输出

## 遇到的问题（已修，代码在仓库 main）

1. **vLLM 0.34.0 拒收超原生上限的 max_model_len。** 首次部署
   （13:52）容器循环重启约 11 分钟，日志报错：`User-specified
   max_model_len (272000) is greater than the derived max_model_len
   (max_position_embeddings=262144.0) ... set the env var
   VLLM_ALLOW_LONG_MAX_MODEL_LEN=1`。光加 `--hf-overrides` 的 YaRN
   参数不够——vLLM 会先校验再应用覆盖。
   已修：`_CONTAINER_ENV` 里加 `VLLM_ALLOW_LONG_MAX_MODEL_LEN=1`
   （YaRN 外推仍由 `--hf-overrides` 的 rope_parameters 负责），
   README 的 YaRN 一节也补了这条。重部署后 2.5 分钟 /health 200。
2. **探测文本构造踩了两个小坑**（都只影响本地脚本，不影响服务）：
   transformers 5.x 的 `apply_chat_template(tokenize=True)` 返回
   BatchEncoding 而非 list，`len()` 得的是键数（2）；《白鲸》首下
   的文件是 Gutenberg 维护页（503），改走 pglaf.org 镜像才拿到正文。
